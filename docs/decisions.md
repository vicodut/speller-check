# Decisions

- 2026-10-30: macOS + Chrome only for v1.
- 2026-10-30: Architecture = Swift helper + Bun/TS core + Chrome extension; the core owns all logic.
- 2026-10-30: One OpenAI-compatible provider adapter; native Anthropic adapter later.
- 2026-10-30: Model returns {original, suggestion, reason, context, type}; the core computes offsets.
- 2026-10-30: Standard international French, not Québec usage.
- 2026-10-30: Core uses plain TS with manual constructor injection, no NestJS.
- 2026-10-30: Expected failures return Result; exceptions only for programmer errors.
- 2026-10-30: Zod schemas in packages/protocol are the single source of truth; Swift types are generated.
- 2026-10-30: Tooling = Bun workspaces, bun test, Biome, SwiftFormat/SwiftLint, XcodeGen.
- 2026-10-30: Provider is a thin transport (`complete(messages) → Result<string>`); prompt, parse and locate live in the check feature. Spec's `check(req): Promise<Issue[]>` replaced.
- 2026-10-30: Issue offsets are UTF-16 code units, `end` exclusive.
- 2026-10-30: One batched request per check with each distinct uncached sentence once, plus neighbouring sentences as context-only; results cached per sentence (sentence-relative offsets, clean = []) by sha256(sentence) + model. Dictionary filter runs after the cache.
- 2026-10-30: Locator: original must be unique among matches inside a matching context, else unique in the checked sentences, else dropped. Whole-word bounds, loose whitespace, ' ≡ ’; `original` is rewritten to the source slice.
- 2026-10-30: Overlapping issues: the first (by start) wins.
- 2026-10-30: Dictionary filter drops an issue when `original` is a term, or contains a term the suggestion changes or removes. Fixes that keep the term survive.
- 2026-10-30: Dictionary file `{ entries: [{ term, note?, caseInsensitive? }] }`; missing file = empty, invalid file = error. Default path `~/Library/Application Support/GrammarChecker/dictionary.json`.
- 2026-10-30: JSON mode via `response_format: json_object`, dropped for the provider's lifetime after a 400/422. temperature 0, 60 s timeout constant (no env var).
- 2026-10-30: Parser strips `<think>` blocks and code fences, accepts a bare array, and drops individual schema-invalid issues instead of failing the batch. The JSON retry resends the prompt plus a reminder, without echoing the bad reply.
- 2026-10-30: Logger only accepts a fixed set of event names and error codes; logs go to stderr so CLI stdout stays pure JSON.
- 2026-10-30: CLI exit codes: 0 ok, 1 check failed, 2 usage/settings error.
- 2026-10-31: Parser drops no-op issues (suggestion equals original after trimming). Seen often with gemma3:4b.
- 2026-10-31: Optional GC_REASONING_EFFORT (none|low|medium|high), sent as `reasoning_effort` only when set. qwen3:8b on CPU: thinking on = >60 s timeout; reasoning_effort none = ~9 s.
- 2026-10-31: WebSocket protocol: clients send `hello {token}` first, then `text.changed`, `field.closed`, `dictionary.add`; the core replies `ready`, `issues`, `error {code, fieldId?}`, `settings.changed`. All messages are a Zod discriminated union on `type` in packages/protocol.
- 2026-10-31: Install token: random, stored in `~/Library/Application Support/GrammarChecker/token` (mode 600), printed by `core token`; pasted into the Chrome options page until the Swift app hands it over (milestone 6). Default port 7341, overridable with `GC_PORT`.
- 2026-10-31: Field sessions (debounce, latest version/text per field) are the second place with in-memory state, next to the cache.
- 2026-10-31: Chrome extension: React card, `bun build` bundling (no extra bundler), write-back via `execCommand("insertText")` with a re-read and Copy fallback. Plain `textarea`/`input` first; `contenteditable` in a second pass.
- 2026-10-31: Reconcile treats the change between snapshot and latest text as one edit (common prefix/suffix); issues touching it are dropped unless the boundary is whitespace on both sides, and survivors must still match `original`. A result is published only if its snapshot is newer than the last published one, so a fresh result replaces a reconciled one.
- 2026-10-31: Server accepts upgrades with no Origin (native client) or `chrome-extension://<32 a–p>` only (403 otherwise); anything but a valid `hello` before auth, or no hello within 5 s, gets `auth_failed` and close 1008. Token compared with `timingSafeEqual`. Max payload 1 MiB.
- 2026-10-31: Token file: 32 random bytes base64url, created with `wx` + mode 600 (dir 700), never overwritten. `core token` needs only GC_PORT/GC_TOKEN_PATH.
- 2026-10-31: `dictionary.add` trims the term, skips exact (case-sensitive) duplicates, writes atomically (temp + rename), never overwrites an invalid file, and queues adds in the repository.
- 2026-10-31: Extension: background prefixes field ids per content port (`p<n>/<id>`) and routes replies only to the owning port; messages are dropped (not queued) until `ready`, then each frame resends its focused field. Blur clears underlines and sends `field.closed`. Blocklist matches host + subdomains, including parent frames. No console logging.
- 2026-10-31: Underline colours: spelling red, grammar blue, punctuation orange, syntax purple. Underlines whose range no longer holds `original` are hidden on input until the next result. The card opens on click or caret navigation inside an issue; Dismiss is per field, in memory. Add to dictionary only for spelling issues or single-word originals.
- 2026-11-01: Chrome shows a spinner in the focused field's bottom-right corner from a change until `issues`/`error` for that version (or blur); its own Shadow DOM, pointer-events none, pulses under reduced motion. Same spot as the future error-count badge. Frame scheduler moved to content/shared.
- 2026-11-01: contenteditable support: the field is the outermost editable element; its text comes from a DOM text model (text nodes in order, `<br>` = "
", one "
" between blocks, a trailing `<br>` in a non-empty block adds nothing, script/style skipped). Underlines use `Range.getClientRects()`; write-back selects the Range and runs `insertText`, then re-checks once after 50 ms (rich editors apply edits late) before falling back to Copy. Offsets inside synthetic newlines are never drawn or edited.
- 2026-11-01: The field badge shows a spinner while checking, then a count (green ✓ for none, red number up to "9+"; click lists the issues and opens the card), orange "!" for a failed check, grey "!" when the core is unreachable or the token is rejected. The background broadcasts `core.status` to content ports (on attach and on change). The list is built with `textContent` only.
- 2026-11-01: Dismissals are keyed on original + suggestion + 12 characters of text on each side (not the offset), so they survive edits elsewhere in the field but not edits right next to the issue.
- 2026-11-01: Prompt: keep the writer's meaning (fix the verb, not the subject), report every error in a sentence, multi-word errors as one issue, `original` = smallest complete wrong phrase, plus one worked example not taken from the fixtures. qwen3:8b fixtures: 16/20 hits (14 accepted) → 19/20 (19 accepted), extras 3 → 2.
- 2026-11-01: The locator trims whole words a suggestion echoes from right before/after `original` ("has went" → "I went" in "I has went" becomes "went"), so Accept can't duplicate them.
- 2026-11-01: Conflicting issues (#1): overlapping ranges keep the earliest-starting issue (ties: shorter); adjacent issues stay, except that leading words of a suggestion that the previous whitespace-adjacent suggestion already ends with (trailing English contractions expanded: 're, 's, n't…) are removed, and the issue is dropped if nothing is left to fix. Logged as counts only.
- 2026-11-01: Site blocklist changes apply live: the content script listens to `chrome.storage.onChanged`; a newly blocked frame stops its field watcher, removes underlines, card and badge and closes its core port (nothing sent afterwards); a newly unblocked frame starts as on load. Ancestor frames still count.
- 2026-11-01: Picking an issue from the badge list scrolls its first line into view (the field, each scrollable ancestor, then the window; instant, with an 8 px margin) before opening the card. The caret and focus are left alone.
- 2026-11-01: Email cleaning (#11): the extension's text model takes a skip matcher; the `email-cleaning` feature builds it per hostname from provider adapters. `blockquote` is skipped on every site; the Gmail adapter skips quote and signature containers by class (`gmail_quote`, `gmail_quote_container`, `gmail_extra`, `gmail_attr`, `gmail_signature`, `gmail_signature_prefix`). Skipped text is never sent; a skipped block still counts as a line break. Textareas and inputs are unaffected.
- 2026-11-01: Rephrase (#9): new core feature `rephrase`, read-only versions in the badge panel. Passage = caret paragraph (blank line ends it) capped around the caret to 8 sentences / 1,500 chars; one model call for four tones answering by sentence number; versions validated against the core's own split; the model reports the language. Failures reuse `error` with `request: "rephrase"` so they never mark the check failed; the background answers `core_unavailable` at once when the core can't take the request. The panel also opens on a clean badge. Own provider instance with a 120 s timeout: qwen3:8b (reasoning none) took ~29 s for a 2-sentence EN passage, ~35 s for 3 FR sentences, 83 s cold.
- 2026-11-02: Rephrase (#14): one model call per tone (Professional, Casual, Concise, Friendlier, in that order), each sent as `rephrase.tone` as soon as it is validated, then `rephrase.done {count}` (or the rephrase error when no tone was valid). Requests carry a client `requestId` echoed on every reply. A newer request, an edit of the passage (`text.changed`), `rephrase.cancel` (background, when a frame port goes away) or the connection closing stops the remaining calls and aborts the one in flight (`rephrase_cancelled`); a blur (`field.closed`) does not, so tones still arrive and the background routes them to the port until the request ends. The extension keeps the result per field (last 5) until the passage changes, across panel close and blur, and puts a "rephrase ready" dot on the badge for unseen tones (never the count). Prompt: every version fixes grammar and spelling; a sentence with an error is never kept. Per-call timeout 60 s, extension backstop 150 s without a tone.
- 2026-11-02: Rephrase timing, qwen3:8b (reasoning none) on the CPU-only i5, Ollama shared with a parallel benchmark: EN 2-sentence passage with errors, warm: first version 8.0 s, all four 32 s (was ~29–40 s for the first and only reply); cold after a model swap: first 74 s, all four 122 s. FR 3 sentences, warm-ish: first 27.6 s, all four 69 s. The EN Casual version now rewrites every sentence (0 kept) instead of "Already fits this tone".
- 2026-11-02: Length cap (#12): `MAX_TEXT_LENGTH = 20_000` sent characters (after email cleaning) lives in `@gc/protocol` with `isTextTooLong`, used by the extension and the core. Over the cap the extension sends `field.closed` instead of `text.changed` (no text leaves the page; pending checks for the field are dropped), clears the underlines and shows a grey "too long" badge (…); a rephrase over the cap is not sent. Back under the cap the text is sent as a new version. The core refuses over-cap text with the new error code `text_too_long` before any model call, in the check service (so `core check` too), the field sessions and the connection handler for `rephrase.request`; logs carry the code and length only.
- 2026-11-02: Rephrase Replace (#10), built on the #14 protocol (`rephrase.tone` per tone, not `rephrase.result`): Replace per rewritten part, Replace all per version as one edit over the whole passage range, both through the Accept write-back (`applyFix` now takes any `{start, end, original, suggestion}`) with the Copy fallback. The extension keeps the parts written per result and maps every range from the original sentences, so parts from different versions combine; a part straddling a replaced part's edge has no button, a part covering replaced parts overwrites them, Replace all always yields that whole version. The result is dropped (never written over) as soon as the field no longer holds the passage with those parts at its offsets.
- 2026-11-02: Rephrase cache (#10): the ticket's "keyed by model + passage hash" became model + passage hash + tone, because #14 made one model call per tone. A repeat request replays the cached tones instantly as `rephrase.tone` messages and only calls the model for missing tones (a tone skipped earlier, or one never reached because the request was cancelled). Passage hash = SHA-256 of the sentences in order (the model never sees the space between them). In-memory LRU, 200 entries; only validated tones are stored. qwen3:8b (reasoning none, CPU-only, warm) on a 2-sentence EN passage with errors: first version 21.2 s, all four 40.3 s; the same request again: all four in under 1 ms, no model call.
- 2026-11-02: Refocus reuse (#15): the extension keeps per field the last sent text and its issues (last 8 fields, memory only, `features/check-memory`). A focus with exactly that text redraws them and sends nothing; edits, other text and the `core.ready` resend check as before. To keep a result still in flight at blur, `field.closed` is deferred until that result or error arrives (60 s backstop, flushed on `core.ready`); the cost is that a check debouncing at blur now runs instead of being dropped. A dictionary addition clears the memory, since the core would now filter some remembered issues.
- 2026-11-02: Batched first checks (#13): uncached sentences go to the model in document-order batches of at most 20 sentences / 3,000 characters (`BATCH_MAX_SENTENCES`, `BATCH_MAX_CHARS` in the core's `check-limits.constants.ts`, next to `DEBOUNCE_MS`), each with its neighbour context and cached as soon as it is done. `CheckService.check` takes optional `onPartial(issues)` (after every batch but the last, all issues so far) and `isSuperseded()` (asked after each batch; true drops the rest and the output says `superseded`); `core check` passes neither. The `issues` message gets optional `pending: true` on every publish but the last of a batched check; field sessions accept partials for the same snapshot until its final (or error) publish. Decided here: a field runs one check at a time, so a newer version waits for the batch in flight instead of resending its sentences in parallel; that batch is still published, as a partial reconciled onto the newer text, then the newer check starts and finds it in the cache. The extension draws partials but keeps the spinner, and only the final result is remembered for refocus or releases a deferred `field.closed`. Timing, qwen3:8b (reasoning none) on the CPU-only Mac, 40 EN/FR sentences (2,625 chars, error-dense, 2 batches of 20): the first run hit the 60 s provider timeout on batch 1 (model just loaded); warm, batch 1 took 39.4 s and batch 2 82.6 s (a 1,758-char reply), so an error-dense 20-sentence batch can exceed the 60 s check timeout on this machine. Limits kept as specified; lowering `BATCH_MAX_SENTENCES` (~10) or raising the check timeout is an open follow-up.
- 2026-11-02: Batch limits lowered to 10 sentences / 1,500 characters (`BATCH_MAX_SENTENCES`, `BATCH_MAX_CHARS`), from 20 / 3,000. On the CPU-only Mac (qwen3:8b, ~7–9 tokens/s) an error-dense 20-sentence batch took 39–83 s and could exceed the 60 s check timeout; half-size batches should stay under it, and the first underlines of a long field appear about twice as soon. The check timeout stays at 60 s.
- 2026-11-05: Keepalive (#16): the Chrome background sends `ping` every 20 s while the core connection is ready, and the core ignores it (no reply, no log). Found in the Chrome test pass: with no WebSocket traffic during a model call over ~30 s (qwen3:8b on CPU), Chrome stopped the MV3 worker, the socket closed, the reply was lost and the badge kept spinning; the core then dropped the remaining batches and a rephrase was cancelled. The worker now stays alive for as long as the core is connected, even with no tab using it; an accepted cost for a local tool.
- 2026-11-05: Rephrase prompt (#17): each tone now gets its own guide with concrete markers (Professional: no "!", "Je serais disponible"/"Could you please"; Casual: contractions, "dispo"; Concise: cut a third; Friendlier: warmth and a closing) and an example of the same passage in that tone, plus a rule that the four tones must be easy to tell apart. Measured with qwen3:8b (reasoning none, temperature 0, CPU-only) on 3 passages (2 FR, 1 EN), word-bag distance between tones (0 = same words, 1 = none shared): FR Indeed reply 0.12 → 0.40, EN 0.37 → 0.51, FR invoice 0.06 → 0.42; per-tone time unchanged (~12–37 s warm). Remaining model limits seen: Friendlier can add a judgement ("looking great overall"), Concise can drop a minor fact or switch tu → vous, Professional can add "Monsieur". Two stricter variants were tried and rejected: more rules were ignored, and French wording in the guides made the EN passage come back in French (1 of 4 tones, then 3 of 4); v1 never translated in 12 calls. A cloud model (#5) is expected to follow the rules better.
- 2026-11-05: Elapsed time (#19): after 10 s of checking, the Chrome badge shows the time spent on the current version next to the spinner ("23s", then "1m 1s" from a minute: the ticket said up to 60, but a batched check can run several minutes), refreshed every second and repeated in the tooltip. It is a label left of the 16 px badge, so the badge position and size are unchanged. Partial results keep the start time; a new version restarts it. Seen while taking README screenshots: a cold qwen3:8b load spun for about a minute with no sign of progress, then failed on the 60 s timeout.
- 2026-11-05: Rephrase tone picker (#18), superseding the #9 "four versions on demand" design: the panel's Rephrase button becomes four tone buttons and a click asks for that tone only, so the version you want costs one model call instead of waiting behind up to four (qwen3:8b on CPU: ~12–37 s per tone). `rephrase.request` gets optional `tones` (non-empty, unique; omitted = all four, so older clients still work); the core makes only those, in display order, replaying cached ones, and `rephrase.done.count` counts that request's tones. Another click adds its version to the same kept result. Since a new request still supersedes the field's running one, the extension sends the union of the tones still missing (in flight + new): the core replays what it already finished, and at worst restarts the tone that was mid-call. Decided here: every further tone is asked on the kept result's original text and caret, so all versions share one passage and Replace keeps working across them; while a result is kept the buttons stay enabled wherever the caret is (the caret-in-a-sentence rule applies to starting a result).
- 2026-11-05: Text edits (#7): new client message `text.edit {fieldId, version, baseVersion, start, deleteCount, insert}` (UTF-16). The Chrome content script (`features/text-edits`) diffs the last text it sent per field (last 8 fields, memory only) with the new one as one contiguous edit (common prefix and suffix, never splitting a surrogate pair) and sends it while typing; focus, the `core.ready` resend, a resync, a closed or over-cap field, and an edit not smaller than the text send the full `text.changed`. The core's transport keeps per connection each open field's last received text and version (dropped on `field.closed`); a matching edit is rebuilt, refused over the cap with `text_too_long` (and its base dropped), then routed exactly like `text.changed`, so field sessions, versioning, reconcile and rephrase are untouched. A mismatch (unknown field, other base, version not moving forward, out of range) gets `error {code: "resync_needed", fieldId}` and no check; the extension resends the focused field's full text as a new version, or releases a blurred field's deferred `field.closed`, and never shows it as a failed check. Logs: `text.edit_applied` (rebuilt length), `text.resync_needed` (code).
- 2026-11-05: Cold model (#23): the first check after the core or Ollama started, or after Ollama unloaded an idle model (5 min by default), failed on the 60 s provider timeout while qwen3:8b loaded (~70 s on the CPU-only Mac; seen three times in one day). Now `core serve` sends a one-token warm-up in the background when it starts listening, and both the check and rephrase providers retry a timed-out call once with a 150 s timeout (`TimeoutRetryProvider`, wired in `main.ts`; a cancelled call is not retried). Keeping the model loaded (Ollama `keep_alive`) is left to the user's Ollama setup, since it holds ~6 GB of RAM while idle. Cost: a check that is genuinely slow (not loading) can now take up to 60 + 150 s before it fails.
- 2026-11-07: Settings over HTTP (#31): the core's 127.0.0.1 port also answers plain HTTP. `GET /api/settings` returns a `SettingsView` (protocol package) per feature, each value with its source; the API key is a strict `{set, source, envVar?}`, so a value can't be added by mistake. Guards: `Host` must be `127.0.0.1:<port>`/`localhost:<port>` (DNS rebinding), `Origin` absent or the core's own (websites and the extension refused), install token as a bearer token. The core has no model defaults yet, so sources are `env` or `unset`; `default` is reserved for saved profiles (#33). The logger gains a `sources` field that keeps only known setting names with a known source word. `ReasoningEffort` moved to the protocol package so the core and the view share it.
- 2026-11-07: Settings page (#32): new `apps/settings-web` package (React 19.3.1, the version the extension already uses: no new dependency), built by `bun build` into `dist/` and served by the core at `/settings` through `SettingsPageFiles`, a repository that maps the three known paths to files (no traversal) and adds a strict CSP. Page state is one reducer; the token comes from the link's `#token=` fragment, is stored in local storage and cleared from the address bar, and a fresh link wins over a stored token. `core settings` opens the link with macOS `open` (prints it if that fails); `bun run dev` builds the page first. The page's API client is tested against a stub server rather than the core's, because apps don't import each other; the core's side is covered by its own server tests. Checked in Chrome on a test core (port 7399): sources shown, token stripped and stored, a reload without the fragment still works, a wrong token shows "run core settings again".
- 2026-11-07: Cloud benchmark (#5), fixtures via OpenRouter (`GC_BASE_URL=https://openrouter.ai/api/v1`), no code change. qwen/qwen3.8-flash: 20/20 hits (20 accepted), 0 extras, ~0.8–2.4 s per case; the best run. qwen/qwen3.7-flash: 20/20 hits (20 accepted), 1 extra ("On a migré" → "Nous avons migré", a style change labelled grammar), ~0.7–4.5 s per case; with 3.8-flash, the only models that got the subjunctive right ("viens" → "viennes"). meta-llama/llama-3.3-70b-instruct: 19/20 (18 accepted), 1 extra; perfect in English, missed "mangé" (object before the verb), flagged the correct "s'est lavé les mains", suggested "vienne" instead of "viennes". mistralai/mistral-small-3.2-24b-instruct: 16/20, 0 extras; missed "Their", "Its", "isnt" and the subjunctive, but left "s'est lavé les mains" alone. Baseline qwen3:8b on Ollama: 19/20, ~9 s per case. Milestone 1's "one cloud model, EN and FR" is met with qwen3.8-flash (and qwen3.7-flash). French past-participle agreement is where models disagree most, so prompt guidance there is a likely follow-up.
- 2026-11-07: Modal dialogs: found on LinkedIn, whose post composer is a modal `<dialog>` (top layer, rest of the page inert), so our underlines, card and badge were drawn under it and could not be clicked. `placeHost` (Chrome `content/shared/top-layer.util.ts`) moves the `gc-overlay` and `gc-status` hosts into the field's `dialog:modal` and shows them as `popover="manual"` (inside the dialog = not inert; popover = top layer above it, `position: fixed` stays viewport-relative); for any other field they stay on `<html>` as plain elements. Called on every redraw and badge placement, which also re-attaches a host the page dropped with its dialog. Checked on LinkedIn: the card opens and Accept writes back in the composer; the messaging box (no dialog) still works.
- 2026-11-07: Elapsed time on hover, superseding the #19 label: with a cloud model a check takes ~1–3 s, so the label that appeared after 10 s was never seen. The time now shows only in a popup while the pointer is on the spinner ("Checking… 2.4s", tenths under 10 s, then "23s" and "1m 1s"), repainted every 100 ms while shown; the spinner drops `pointer-events: none` so it can be hovered, and loses its native tooltip so the two do not overlap. The popup is its own class (`elapsed-popup.service.ts`), which brings `status-badge.service.ts` back under 200 lines.
- 2026-11-07: Saved profiles with live switching (#33): `core serve` no longer needs `GC_*` env vars. Profiles live in `settings.json` (`SettingsFileRepository`, Zod-validated, temp file + rename), managed by `SettingsService`, which saves first and only then tells its listeners when the model in use actually changed. Env vars still win, as a whole: any of the four model vars set makes a locked env model (no mixing with a profile), so dev setups keep working; `SettingSource` gains `saved`. Whether a profile is local is derived from its base URL host, never typed in, so a cloud URL can't be mislabelled local. A switch swaps both `SwitchableProvider`s, clears `CheckCache` and warms up; `WebSocketServer.broadcast` sends `settings.changed` to authenticated connections only. The extension background maps it to `core.model_changed` for every frame, which forgets results, resets edit bases and re-sends the focused field. `scripts/dev.ts` no longer injects `GC_BASE_URL`/`GC_MODEL` defaults; it reads the active profile only to decide whether to start Ollama. Checked in Chrome on a test core (port 7399): first run created Local, an OpenRouter preset was added and activated, both features switched live, the log showed `settings.switched` with no values.
- 2026-11-07: The first-run Local profile is built in (#33 review): it can be edited but never deleted (`profile_builtin`, 409), so there is always a local fallback; the page hides its Delete button. The settings file records it as `builtInProfileId`; a file saved before that field marks its first local profile on open.
- 2026-11-07: `bun run dev` starts Ollama whenever it's installed, not only when the active profile is on it (#33 review): with a cloud profile active at startup, switching to Local in the settings page found no Ollama (`provider_network`). Ollama is required, with the model pulled, only when the model in use at startup is on it; otherwise starting it is best effort. Stopped on Ctrl-C if dev started it. Interim until the core manages the local runtime (#39, #41).
- 2026-11-07: API keys in the Keychain (#34): `SecurityKeychain` (core settings feature, a repository: it touches the system store) wraps `/usr/bin/security`, no dependency. The key is written through `security -i` on stdin so it never shows in `ps`; that format needs the key inside double quotes, so keys are limited to printable ASCII without quotes, backslashes or spaces (`ApiKey` in the protocol), which every provider key we know fits. Profile POST/PUT take an optional `apiKey` (set / `null` remove / absent keep) instead of separate key routes, so one save is one request. The key is stored before the profile is saved (and removed again if the save fails), so a profile never claims a key the Keychain refused. The service keeps only which profiles have a key, reads the key when the active model is built, and re-switches when the active profile's key changes. Checked on a test core: a keyed profile pointed at a local stub sent the right `Authorization` header on activation; the key never appeared in responses, `settings.json` or the log; deleting profiles removed their Keychain items.
